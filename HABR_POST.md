# Как я написал интерактивный САПР для проектирования локальных сетей (ЛВС/СКС) в браузере на чистом Canvas: от графов Дейкстры до автогенерации спецификации

Привет, Хабр! 

Каждый, кому хоть раз доводилось проектировать локальную вычислительную сеть (ЛВС) или структурированную кабельную систему (СКС) для офиса, склада или небольшого предприятия, знает эту рутину. 

Обычно процесс выглядит так:
1. Заказчик или коллега скидывает план этажа (в лучшем случае PDF или DWG, в худшем — скан на салфетке).
2. Вы открываете Visio, AutoCAD или LibreCAD.
3. Вручную расставляете розетки, рабочие места, камеры и точки доступа.
4. Долго и нудно вычерчиваете ломаные линии кабель-каналов через двери и стены.
5. Затем берете рулетку/инструмент измерения длины, выписываете метражи в Excel, прибавляете вертикальные спуски по 1.5 метра к розеткам, накидываете 10% «на изгибы и разделку», делите на 305 метров, чтобы понять, сколько бухт заказывать, и подбираете по портам коммутаторы.

Если планировка меняется (а она меняется *всегда*), цикл повторяется заново.

В какой-то момент мне надоело тратить часы на эту механическую работу. Захотелось сделать инструмент, работающий по принципу **«в один клик»**: набросал план помещений на координатной сетке, расставил требования по рабочим местам, ткнул «Сгенерировать сеть» — и получил оптимальные кабельные трассы, автоматически расставленные коммутаторы и готовую смету оборудования (BOM) с выгрузкой в CSV.

Так родился **Network Planner** — открытый легковесный веб-инструмент без зависимостей, фреймворков и бэкенда.

В этой статье я расскажу:
* Как устроена дискретная модель стен и помещений в HTML5 Canvas;
* Как оптимизированный алгоритм Дейкстры на двоичной куче (`MinHeap`) прокладывает кабельные трассы с учетом дверей и физических препятствий;
* Как решается задача выбора места под коммутаторы и почему топология должна быть гибридной (Star + Home Run);
* С какими неочевидными краевыми случаями геометрии мы столкнулись на практике (включая баг «почему не отрисовалась Комната 2»);
* Как автоматически считаются запасы витой пары и активное сетевое оборудование.

## 1. Архитектурные принципы и почему Zero Dependencies

Когда начинаешь новый фронтенд-проект в 2020-х годах, первой мыслью часто бывает: *«Возьму React/Vue, подключу Konva.js/Fabric.js, накачу Tailwind и настрою Vite»*. 

Но для инженерного чертёжного инструмента такой подход часто создает оверхед:
* Инженерные чертежи требуют отрисовки сотен отрезков стен, кабелей, бейджей и меток со скоростью 60 FPS при панорамировании и драге.
* Проект должен запускаться где угодно: на корпоративном ноутбуке без интернета, прямо из локальной папки или на флешке у сетевого монтажника.

Поэтому стек был выбран предельно минималистичный:
* **HTML5 Canvas 2D** — для рендеринга чертежа, сетки, оборудования и кабелей;
* **Vanilla JavaScript (ES6+)** — без сборщиков, транспиляторов и внешних npm-пакетов;
* **Нативный CSS** — для интерфейса, модальных окон и боковой панели.

Весь проект — это пара файлов (`index.html`, `style.css`, `app.js`), которые открываются двойным кликом в браузере.

## 2. Дискретная пространственная модель: Стены, Сетка и Шлюзы

### Координатная сетка
В основе лежит метрическая сетка. Масштаб выбран так: **1 метр = 28 пикселей**.
Каждое помещение — это прямоугольная область с координатами верхнего левого угла `(x, y)` в метрах и габаритами `(w, h)` в метрах.

Для удобства проектировщика мы добавили:
1. **Координатные линейки (Rulers)** сверху и слева с автоматической разметкой и динамическими маркерами текущей позиции курсора.
2. **Двухуровневую сетку**: вспомогательные линии каждый 1 метр и акцентные контрастные линии каждые 5 метров.
3. **Интерактивное растягивание комнат мышкой** (нажали `[7]` или `R`, зажали ЛКМ и растянули комнату нужного размера с живой подсказкой площади в $м^2$).
4. **Магнитное прилипание (Smart Snapping)**: при перетаскивании комнаты выравниваются «стена-к-стене» к соседним помещениям.

### Как адресуются стены?
Стены не хранятся как произвольные отрезки в вещественных координатах. Они привязаны к границам между ячейками сетки:
* `H:x:y` — горизонтальный сегмент стены длиной 1 метр между строками $y$ и $y+1$ по координате $x$.
* `V:x:y` — вертикальный сегмент стены длиной 1 метр между столбцами $x$ и $x+1$ по координате $y$.

```javascript
function getRoomBoundaryWalls() {
    const result = new Set();
    rooms.forEach(room => {
        // Верхняя и нижняя границы
        for (let x = room.x; x < room.x + room.w; x++) {
            result.add(`H:${x}:${room.y}`);
            result.add(`H:${x}:${room.y + room.h}`);
        }
        // Левая и правая границы
        for (let y = room.y; y < room.y + room.h; y++) {
            result.add(`V:${room.x}:${y}`);
            result.add(`V:${room.x + room.w}:${y}`);
        }
    });
    return result;
}
```

Благодаря строковым идентификаторам типа `H:7:5`, проверка наличия стены, двери (`doors.has(id)`) или технологического отверстия (`penetrations.has(id)`) выполняется за константное время $O(1)$.

## 3. Трассировка кабелей: Алгоритм Дейкстры и MinHeap

### Почему наивная реализация не подошла?
В первой версии поиск пути использовал стандартный массив и метод `shift()` / линейный поиск минимального расстояния. На плане с 5–10 комнатами и 30 устройствами генерация начинала ощутимо подтормаживать (до нескольких секунд), так как поиск кратчайшего пути запускается сотни раз (для каждого устройства, для шлюзов выхода и магистральных линков).

Мы перевели алгоритм Дейкстры на собственную легковесную реализацию **двоичной кучи (`MinHeap`)**:

```javascript
class MinHeap {
    constructor() { this.heap = []; }
    push(node) {
        this.heap.push(node);
        this._siftUp(this.heap.length - 1);
    }
    pop() {
        if (this.heap.length === 0) return null;
        const top = this.heap[0];
        const last = this.heap.pop();
        if (this.heap.length > 0) {
            this.heap[0] = last;
            this._siftDown(0);
        }
        return top;
    }
    _compare(a, b) {
        return a.cost - b.cost || a.order - b.order;
    }
    // _siftUp и _siftDown за O(log N)
}
```

Сложность поиска пути упала до $O(E \log V)$, а вся генерация сети для этажа из 5 комнат и 30 устройств стала занимать **менее 20 миллисекунд**.

### Штрафы за проход через стены
Кабель в СКС не может летать по диагоналям сквозь стены. Он должен идти по коридорам, заходить в комнаты через двери или кабельные проходки (гильзы).

Для этого в граф переходов заложена система весов:
* Свободный шаг по коридору или внутри комнаты: вес `1`.
* Шаг сквозь дверь (`door`) или согласованную кабельную проходку (`penetration`): вес `1`.
* Шаг сквозь сплошную стену без проема: вес `1 + PENETRATION_PENALTY` (штраф **50**).
* Шаг транзитом через чужую комнату: штраф **+12**.

Алгоритм сначала всеми силами ищет путь по открытым коридорам и дверям. И только если прохода физически нет, он «пробивает» стену в оптимальной точке, автоматически предлагая проектировщику добавить кабельное отверстие.

## 4. Иерархия топологии: когда ставить свитч, а когда тянуть Home Run?

В реальном сетевом проектировании никто не ставит отдельный коммутатор в комнату ради одного компьютера. Это экономически нецелесообразно.

Поэтому в планировщике заложена строгая инженерная логика:

1. **Комнаты с $\ge 3$ устройствами**:
   * В комнате создается **локальный коммутатор доступа** (Access Switch).
   * Если среди устройств есть IP-камеры или точки Wi-Fi, коммутатор автоматически помечается как **PoE**.
   * Абонентские кабели сходятся к этому коммутатору внутри комнаты (`access`).
   * От коммутатора через шлюз на стену выходит один магистральный линк (`uplink`) к серверной или роутеру провайдера.
2. **Комнаты с $< 3$ устройствами**:
   * Коммутатор не выделяется.
   * От каждого устройства строится прямая физическая линия (**Home Run**) через дверь/отверстие напрямую в серверную.
3. **Серверная комната (ISP / Core)**:
   * Является центральной точкой схождения всех магистралей.
   * Устройства внутри серверной подключаются локально без вывода кабелей в общий коридор.

## 5. Грабли из реальной разработки: почему не отрисовалась «Комната 2»?

На этапе тестирования пользователи прислали скриншот: на плане 5 комнат. В Комнате 1, 3, 4 есть коммутаторы и кабели. В Комнате 5 стоит роутер провайдера. А **Комната 2 (в которой 4 ПК, камера и Wi-Fi) осталась абсолютно пустой** — ни одного кабеля и ни одного свитча.

Вскрытие показало три взаимосвязанные проблемы:

### Грабли №1: Рассинхронизация `networkEntry.roomId`
Когда пользователь перетаскивал точку ввода сети в Комнату 5, в объекте `networkEntry` оставался старый `roomId = "r2"`. 
В цикле генерации сети стояла строчка:
```javascript
if (room === entryRoom) continue; // Пропускаем серверную!
```
Планировщик посчитал Комнату 2 серверной и пропустил её! А ветка подключения локальных устройств серверной не сработала, потому что фактические координаты `(x, y)` роутера находились в Комнате 5.

**Решение**: ввели строгую динамическую синхронизацию в `ensureEntry()`:
```javascript
const actualRoom = getRoomAtCell(networkEntry.x, networkEntry.y);
networkEntry.roomId = actualRoom ? actualRoom.id : null;
```

### Грабли №2: Отсечение шлюзов на смежных стенах
Функция поиска шлюзов комнаты отбрасывала точки выхода, если внешняя клетка касалась другого помещения: `if (isInsideRoom(outside)) discard()`. 
Если стена была общей между двумя кабинетами, даже при наличии двери она объявлялась «невалидной», и комната оставалась без шлюза в мир.

**Решение**: двери и отверстия на смежных стенах теперь сохраняются как легитимные шлюзы, плюс реализован список `fallbackGateways`.

### Грабли №3: Двухуровневый магистральный роутинг
Если коридор плотно зажат комнатами или перекрыт перегородками, строгий коридорный поиск заходил в тупик.
Мы внедрили **двухуровневый каскад**:
1. Сначала ищется чистый путь по свободным коридорам (`allowRoomPenetration = false`).
2. Если путь не найден, алгоритм не падает с ошибкой, а автоматически перезапускает поиск с флагом `allowRoomPenetration = true` и умеренным штрафом за транзит сквозь комнаты. 100% гарантия соединения узлов!

## 6. Автоматический расчет спецификации (BOM)

Мало нарисовать красивые линии — монтажникам и закупщикам нужна смета.

В планировщик встроен калькулятор спецификации, который учитывает физику монтажа СКС:

```javascript
function calculateSpecification() {
    const VERTICAL_DROP_PER_DEVICE = 1.5; // Спуск по стене к розетке (м)
    const CABLE_SAFETY_MARGIN = 1.10;      // +10% технологический запас на разделку

    const totalHorizontalMeters = lastCableLength;
    const totalDevices = pcCount + printerCount + cameraCount + wifiCount;
    
    // Суммарный метраж вертикальных опусков
    const totalVerticalDrops = Math.round(totalDevices * VERTICAL_DROP_PER_DEVICE);
    
    // Итоговый метраж кабеля
    const totalEstimatedCable = Math.ceil((totalHorizontalMeters + totalVerticalDrops) * CABLE_SAFETY_MARGIN);
    
    // Количество стандартных бухт по 305 метров
    const cableBoxes305m = Math.ceil(totalEstimatedCable / 305);
    
    // Коннекторы RJ-45: по 2 на устройство + по 2 на коммутатор + резерв
    const rj45Connectors = totalDevices * 2 + localSwitches.length * 2 + 4;
    ...
}
```

А по кнопке **«📊 Спецификация (CSV)»** формируется структурированный файл, готовый для импорта в Excel или 1C:
* Марка кабеля («Витая пара UTP Cat 5e / 6»);
* Общий метраж и число бухт (305 м);
* Модели и портовость коммутаторов (5, 8, 16, 24 порта, Standard/PoE);
* Количество коннекторов RJ-45 и розеток.
